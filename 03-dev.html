Enfoque 03

IA para un dev

Un agente en la terminal que lee el repo, edita archivos y corre comandos. Cómo se configura con Claude Code y cómo se mantiene bajo control.

Ejemplos con Claude Code; la mayoría de las ideas aplican a otros agentes de código (Copilot agent, Cursor, Codex). Datos verificados contra code.claude.com/docs.

Del autocompletado al agente

  • Autocompletado: sugiere la próxima línea. Vos decidís.
  • Chat en el IDE: responde y propone cambios. Vos copiás.
  • Agente (Claude Code): planifica, lee archivos, edita, corre tests y comandos en tu máquina, con tus permisos.

El mismo salto que veremos en el enfoque 06: de decir a hacer.

Es sumar a alguien al equipo que trabaja en tu notebook, con tu usuario. Le das un manual (CLAUDE.md), recetas (skills) y reglas de la casa que no puede saltear (permisos y hooks).
La analogía organiza el resto del deck: manual, recetas y reglas de la casa.

Las piezas: sugerencias vs. controles

Clave de seguridad: lo amarillo es una sugerencia que el modelo puede no seguir (o una inyección puede hacerle ignorar). Lo verde lo aplica Claude Code siempre.

Esta distinción es la idea más importante del deck. "No borres archivos" en CLAUDE.md es un pedido; un deny en permisos o un hook es una regla.

Jerarquía de memoria: qué instrucciones lee Claude

Verde = cargado en el contexto. Tocá una capa para ver el detalle.

Mostrar primero "recién arranca": ancestros y rules sin paths. Después src/api/users.ts: se suman src/api/CLAUDE.md y la rule con paths. Remarcar: las capas se SUMAN, no se pisan. Si se contradicen, el modelo elige; por eso conviene no contradecirse. /context muestra qué se cargó.

Jerarquía de settings: quién gana

Managed (organización)› Línea de comandos› .claude/settings.local.json› .claude/settings.json› ~/.claude/settings.json

Valores simples

Para un valor (modelo, tema…) gana el scope más alto de la lista.

Listas de permisos

Se combinan todas. Después se evalúa: deny → ask → allow. Un deny en cualquier scope bloquea aunque otro permita.

Managed

Lo instala la organización (MDM, servidor). No se puede pisar desde el usuario ni el proyecto.

Como las normas de un edificio: el reglamento del consorcio (managed) manda sobre las reglas de cada departamento, y si cualquiera dice "prohibido", está prohibido.
Precedencia de valores ≠ orden de evaluación de reglas de permisos. La próxima slide lo muestra en vivo.

Qué esInstrucciones y recursos (scripts, plantillas) que Claude carga cuando hacen faltaUn atajo /nombre que dispara un promptOtra instancia de Claude que trabaja aparte

Quién lo disparaVos con /nombre, o Claude si la descripción encajaVos con /nombreClaude cuando delega, o vos si se lo pedís

    
Herramientas y modeloLos de la sesiónLos de la sesiónLos suyos: lista propia y hasta otro modelo

  

  

    
¿Cuándo un subagente? Para no llenar el contexto (lee 50 archivos y vuelve solo la conclusión), para limitar permisos (un revisor con solo Read, Grep, Glob) o para trabajar en paralelo. Costo: más tokens y se pierde detalle en el traspaso.

    
Sin tecnicismos: la skill es un instructivo que abrís y seguís vos; el command, un botón de marcado rápido a ese instructivo; el subagente, pedirle la tarea a un colega que la hace en su escritorio, con sus propias llaves, y te devuelve un informe.

  

  
Skills y commands hoy son casi lo mismo: un archivo en .claude/commands/ y una skill con el mismo nombre crean el mismo /comando; lo nuevo se escribe como skill. El subagente con herramientas acotadas es mínimo privilegio, igual que en LLM06 del lab.






  
¿Cómo sabe qué es una vulnerabilidad?

  
Caso: /security-review. El archivo no tiene una base de vulnerabilidades: es un prompt. Cada pieza aporta algo distinto.

  

    
PiezaQué aportaLímite

    
Prompt (el .md)Categorías a revisar, criterio de gravedad, "solo si hay más de 80% de confianza", un paso que filtra falsos positivosOrienta, no sabe

    
Modelo (entrenamiento)Reconoce inyección, XSS, autorización rota… porque leyó mucho código, CWE, OWASP y arreglos de fallas. Razona sobre el código: encuentra fallas de lógicaNo conoce CVE posteriores a su entrenamiento; no es determinístico; puede inventar

    
Herramientasosv-scanner, npm audit, Trivy, un MCP de avisos de seguridad: datos actualizados de qué versión es vulnerableNo saben si tu código usa la parte afectada

    
SkillsConocimiento propio: patrones de tu stack, reglas de la organización, incidentes pasados, y cómo usar las herramientasSon estáticas: envejecen si nadie las mantiene

  

  

    
Combinación
La herramienta dice qué es vulnerable hoy; el modelo razona si te afecta; la skill pone tus reglas. Más SAST (Semgrep, CodeQL) en el pipeline y revisión humana.

Hooks: el momento de cada control

  

    SessionStart→UserPromptSubmit→PreToolUse→herramienta→PostToolUse→Stop→SessionEnd
  

  

    
PreToolUse
Antes de ejecutar. Puede bloquear (exit code 2) y explicarle a Claude por qué. Ej: impedir rm -rf, lecturas de .env, push a main.

    
PostToolUse
Después de ejecutar. Ej: formatear o lintear el archivo editado, registrar la acción.

    
UserPromptSubmit / Stop
Al recibir el pedido o al terminar. Ej: agregar contexto, detectar secretos pegados, correr tests antes de dar por terminado.

  

  
El hook recibe por stdin un JSON con tool_name y tool_input (para Bash, tool_input.command). Hay más eventos; estos son los principales.

  
Los hooks corren con tus permisos: un hook de un repo ajeno es código que ejecutás. Revisarlos como cualquier script.






  
Riesgos propios del agente de código

  

    
Secretos en el contexto
Lee .env, logs o configs y los manda al proveedor. Defensa: deny de Read(./.env), secretos fuera del repo.

    
Permisos de más
bypassPermissions o allow amplios tipo Bash(*). Defensa: allow puntuales, ask para lo irreversible, sandbox o contenedor.

    
Inyección desde el repo
Un README, issue, dependencia o CLAUDE.md de un repo clonado con instrucciones plantadas. Defensa: revisar repos ajenos, permisos estrictos, no confiar en el texto.

    
Terceros LLM03
Servidores MCP, plugins y skills de otros: código y texto que entra con tu sesión. Defensa: solo fuentes confiables, revisar antes de instalar.

  

  
Los cuatro son LLM01/LLM02/LLM06 vistos desde la terminal del dev.
